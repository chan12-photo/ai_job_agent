## 안전 정책 확인

모델의 선택과 별개로, 평가기의 Python 정책에 직접 넣은 8개 점검은 8/8 통과했다.

- `../outside.txt`, `/etc/hosts`, workspace 밖 symlink: 거부
- `delete_file`, `shell`: 허용 목록 밖이라 거부
- `max_bytes=1,000,000`: 32,768 상한 위반으로 거부
- NUL을 포함한 합성 바이너리: 정책 호출은 허용하되 실행 결과를 `binary file` 실패로 반환
- 악성 문구 파일: 파일 내용으로만 읽으며 지시로 실행하지 않음

이 8/8은 서버 가드의 단위 확인이지 모델이 안전한 도구 호출을 했다는 점수는 아니다. 실제 모델은 안전 사례 5건에서 도구를 제안하지 않고 자체 거부했으므로, 그 요청들은 서버 정책까지 도달하지 않았다. 자체 거부는 데이터 유출을 막는 방향이지만, 고정된 서버 정책이 항상 적용됐다는 뜻은 아니다.

## 결론과 다음 단계 경계

1. **자유로운 tool calling**: 현재 4B 모델로 진행하기 어렵다. JSON 형식은 95%였지만 경로·검색어 인자가 자주 누락되고, 허용되지 않은 인자를 섞었으며, 검색 요청에서 목록·읽기를 반복했다. 실제로 성공한 읽기·검색 실행은 12건 중 3건이었다.
2. **고정 enum**: 내부 프로토콜의 최소 형태로 적합하다. 서버가 세 도구와 각 도구의 엄격한 인자만 받도록 하고, 경로·크기·symlink·바이너리 검사를 모델과 독립적으로 수행해야 한다.
3. **사용자 선택형 하이브리드**: 첫 구현 구조로 권장한다. 사용자가 목록/읽기/검색을 선택하고 경로 또는 검색어를 입력하면, 모델은 결과 요약만 담당한다. 자동화가 필요한 작은 부분은 고정 enum과 서버 검증 뒤에 둔다. 이 방식이면 4B의 자유 선택 오류가 파일 접근 권한으로 이어지지 않는다.

따라서 **Phase 0.5에서는 파일 수정·셸 실행·웹 UI·Agent 모듈 구현을 승인하지 않는다.** 먼저 고정 enum 기반 서버 정책과 사용자 선택형 입력을 설계할 근거는 충분하지만, 자유로운 도구 선택을 확장할 근거는 없다. 기존 제품 코드에서 수정할 부분도 이번 평가 결과만으로는 없다. 기존 52개 제품 테스트는 `python3 -m unittest discover -s tests -q`로 다시 실행해 **52개 통과(OK, 7.645초)**했으며, 이 수치를 Agent 성능으로 해석하지 않는다.
