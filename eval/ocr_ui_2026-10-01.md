# 이미지 공고 입력 구현·재검토 기록 — 2026-10-01

## 범위와 환경

PNG/JPG/JPEG 업로드 → 로컬 OCR → 원본 대조·수정·확인 → 기존 공고 등록을 구현했다. match-v5, 요구사항 판정, 기존 검색·분석 기준은 변경하지 않았다. 모델 호출이나 기존 매칭 품질 평가는 다시 실행하지 않았다.

직접 실행한 환경은 사용자 Mac의 Apple M5 Pro, RAM 24 GiB, macOS 27.0.1 (26A434), Python 3.14.7이다. `/usr/bin/swift`와 `/usr/bin/sips`가 이미 설치되어 있었다. 원격 실행 환경의 사양이 아니다.

OCR 엔진은 macOS 내장 Apple Vision 하나다. 실행 중 지원 언어를 조회해 ko-KR·en-US 지원을 확인했다. VNRecognizeTextRequest의 accurate, 한국어·영어 지정, 언어 자동 감지, 언어 교정 끄기 설정을 사용한다. 관측된 글자를 반환하며 빈 곳을 모델로 보충하지 않는다. 별도 패키지·언어 모델 다운로드, API 비용, 외부 전송을 추가하지 않았다. Apple OS 프레임워크를 사용하며 오픈소스 엔진이라고 주장하지 않는다.

공식 자료: [이미지 텍스트 인식](https://developer.apple.com/documentation/vision/recognizing-text-in-images), [지원 언어 확인](https://developer.apple.com/documentation/vision/vnrecognizetextrequest/supportedrecognitionlanguages()), [인식 언어 설정](https://developer.apple.com/documentation/vision/vnrecognizetextrequest/recognitionlanguages).

## 구조와 재검토에서 보완한 부분

- `job_agent/ocr_vision.swift`: 이미지 경로를 받아 Vision의 인식 줄·좌표를 JSON으로 출력한다. 행 위치와 가로 위치로 정렬한다. 다단 문서의 의미상 읽기 순서를 보장하지 않는다.
- `job_agent/ocr.py`: 실제 형식·크기·해상도 검증, 임시 초안과 원본 파일, Swift 실행, 확정 등록을 담당한다. 기존 `app.register`를 호출한다.
- `job_agent/storage.py`: 이미지 연결 테이블과 중첩 트랜잭션을 추가했다. 기존 중복 판단을 그대로 사용한다.
- `job_agent/web.py`: 업로드·순서 변경·삭제·OCR 진행·수정·확인 등록·원본 재조회를 연결한다. 분석은 별도 실행이다.
- `tests/test_ocr.py`, `tests/fixture_ocr.swift`: 명시적으로 가상인 공고 이미지와 별도 임시 DB로 검증한다. 테스트 이미지 자체는 저장소에 넣지 않는다.
- `pyproject.toml`, `.gitignore`: Swift 실행 파일을 패키지에 포함하고 `.assets` 원본·추출문 폴더를 Git에서 제외한다.

재검토에서 다음을 수정했다.

1. 공고 저장과 이미지 연결을 같은 SQLite 트랜잭션으로 묶었다. 연결 실패 시 공고·연결을 함께 롤백하고 새로 복사한 이미지를 제거하며 업로드 초안은 재시도를 위해 보존한다.
2. 등록 시 최종 편집문을 이미지별 문구로 자동 재구성하지 않는다. 사용자가 최종 입력란에 남긴 내용을 그대로 기존 등록 함수로 전달한다.
3. 초안의 24시간 기준을 최초 생성 시각으로 통일했다. 임시 저장했다고 보관 기간이 늘어나지 않는다. 미등록 초안은 이미지 첫 화면에서 다시 열 수 있다.
4. 이미지 저장 중 부분 파일·메타데이터 임시 파일을 정리한다. 같은 공고에 추가 이미지 묶음을 연결하면 기존 이미지 다음 순서에 붙인다.
5. 원본 옆 이미지별 추출문에도 오류가 남을 수 있음을 알리고, 등록된 최종 원문과 구별한다.

브라우저 시험은 별도 임시 DB의 127.0.0.1:18765에서 수행했다. 실제 기본 DB에 가상 공고를 넣지 않았다. 실제 브라우저로 파일 선택, 두 장 업로드, OCR 실행, 최종 원문 수정, 확인란 선택, 등록, 재조회·재시작 후 원본 표시까지 확인했다. 이미지별 순서·개별 삭제의 조작 검증은 HTTP 자동 테스트로 수행했다.

반영 전 기본 DB를 SQLite backup API로 `~/Library/Application Support/AIJobAgent/backups/before-image-input-20261001-131121.sqlite3`에 백업했다. 기존 6개 테이블은 모두 0건이었고 반영 후에도 그대로였다. 이미지 연결 테이블만 빈 상태로 추가됐다. 전후 `PRAGMA integrity_check`는 모두 `ok`였다. 기존 서버를 정상 종료하고 새 코드로 127.0.0.1:8765를 재시작했다. 첫 화면과 `/ocr`가 HTTP 200을 반환하고 실제 브라우저에 업로드 화면이 표시되는 것을 확인했다. 테스트 서버는 종료했다.

가상 첫 이미지에는 `필수 Python 3년`, `SQL 경험 없음`, `마감 2026-10-31`과 오른쪽의 다른 디자인 직무가 있었다. 실제 첫 이미지 출력은 다음과 같다.

```text

[다른 직무] 디자인
SQL 경험 없음
우대 Figma 2년

```

두 번째 이미지의 실제 출력:

```text
[가상 공고] 두 번째 페이지
English reports required

```

브라우저에서 최종 원문을 다음으로 수정해 저장·재조회를 확인했다. 날짜 필드는 별도로 입력하지 않아 마감일 상태는 미확인으로 유지됐다. 지원 상태는 관심, 분석 기록은 0건이었다.

## 저장·정리와 한계

한 번에 1~5장, 한 장 8 MiB, 합계 30 MiB, 한 변 8000픽셀, 전체 2400만 픽셀 이하다. 미등록 초안은 생성 후 24시간이 지나면 다음 이미지 화면 접속·업로드 때 정리한다. 등록 원본은 DB 옆 `<DB파일명>.assets/images`에 계속 보관하고 자동 삭제하지 않는다. DB와 자산 폴더를 함께 백업해야 원본도 보존된다.

일반 저장 예외의 롤백은 검증했다. 전원 차단처럼 파일 복사와 DB 커밋 사이에서 프로세스가 즉시 종료되면 연결되지 않은 복사본이 남을 수 있다. 전원 차단 시험과 자동 고아 파일 정리는 이번 범위에 없다. OCR 중 서버 종료 시 미완료 결과는 복구하지 않으며 초안에서 다시 실행해야 한다. 서버 한 개로 사용한다.

가상 이미지의 일부 글자조차 오독했고 두 열의 의미상 구분도 유지되지 않았다. 실제 공고 전반의 정확도, 흐린 촬영본, 복잡한 표·장식 서체, 다른 macOS 버전은 검증하지 않았다. 사용자가 마감·경력 연수·부정·필수/우대·직무 경계를 직접 확인해야 한다. 신뢰도 점수는 표시하지 않는다. 기존 분석은 3000자 제한을 유지하며 긴 공고를 자동으로 잘라 분석하지 않는다.

추가 모델·다운로드·AI 검토 단계·Phase 5·설치 패키지는 도입하지 않았다.

## 후속 편의 기능 — 클립보드·끌어놓기

`job_agent/image-input.js`를 추가해 붙여넣기 이벤트의 이미지와 끌어놓은 파일을 기존 multipart 업로드 양식에 연결했다. 클립보드를 주기적으로 읽거나 외부로 전송하지 않는다. 파일 선택·붙여넣기·끌어놓기 모두 같은 서버 검사를 거친다. JavaScript가 없으면 기존 파일 선택을 사용할 수 있다. 스크립트는 로컬의 고정 경로에서 제공하며 인라인 스크립트는 허용하지 않는다.

별도 테스트 DB에서 실제 브라우저의 이미지 클립보드와 Command+V로 추가되는 것을 확인했다. 연속 붙여넣기, 6번째 이미지 거부, 개별 제거, 파일 선택으로 JPEG 추가, PNG·JPEG 두 장이 원본 확인 화면에 전달되는 것까지 성공했다. OCR 관련 기존 테스트 11건도 다시 통과했다. 운영체제 캡처 단축키 자체와 Finder에서 브라우저로 끌어놓는 물리적 드래그는 직접 자동화 검증하지 않았다. 다른 브라우저별 호환성도 검증하지 않았다. 기존 OCR·등록·매칭 로직에는 변경이 없다.
